# October 2026 audit — release pipeline, Android configuration, website and documentation

Date: 11 October 2026. This page covers one part of the audit-fix pass: the release pipeline, CI, Android host configuration, the public website and the documentation. Backend (migrations, Edge Functions) and app-code fixes from the same pass are described in their own commits and pull requests.

Nothing here was compiled or run on a device: the work was done without a Flutter SDK, so the first proof is the GitHub Actions run on the merged commit. Section 3 lists what only the owner can do, in consoles this repository has no access to.

## 1. What the audit found in this area

| Finding | Effect |
| --- | --- |
| The release workflow built the AAB without `SUPABASE_URL` and `SUPABASE_ANON_KEY` | Any bundle it produced opened on the "incomplete configuration" screen and nothing else |
| The release workflow could be started from any branch, read repository-level signing secrets without approval, and put its inputs straight into a shell command | Anyone with write access to any branch could sign an arbitrary build |
| Workflows used a moving `stable` Flutter and action tags such as `@v5` | Builds were not reproducible and trusted whatever a tag pointed to that day |
| No `pubspec.lock` was committed | Dependency versions were resolved fresh on every build |
| The site deployed to production without waiting for its own checks | A broken page could go live |
| Android allowed cloud backup and device transfer of app data, and accepted `http` App Links | A session could leave the phone in a backup; an unencrypted link could open the app |
| An unused `google_sign_in` dependency, a committed IDE file, and an SDK constraint lower than the code needs | Unneeded native code in the bundle; misleading requirements |
| The privacy policy did not mention staff accounts, notifications, warehouse records, hosting, retention or user rights, and described deletion vaguely. Pages gave different contact addresses | The public promise did not match the product |
| `robots.txt` blocked a page that also carried `noindex` | Crawlers never see a `noindex` on a page they may not fetch |
| Documents ticked the release workflow and the security phase as complete, gave stale migration counts, and described delivery states that Courier Dispatch V2 replaced | Readers were told work was finished that was not |

## 2. What changed

**Release workflow** (`.github/workflows/android_release_bundle.yml`)

- Runs only from `refs/heads/main` or a `v*` tag; a first job without secrets rejects other refs and malformed inputs.
- The signing job runs in the GitHub Environment `release`.
- Inputs are passed through `env:` and validated with regular expressions.
- `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `AUTH_REDIRECT_URL` come from repository or environment variables, are passed as `--dart-define`, and an empty one stops the run with a clear message. A service-role key is rejected.
- The keystore is written to the runner's temporary directory immediately before the build and deleted right after it.
- The bundle is built with `--obfuscate --split-debug-info`; symbols are a separate artifact. The AAB artifact is kept 3 days.

**All workflows in this area** (`flutter_ci.yml`, `identity_checks.yml`, `pages.yml`, `website_checks.yml`, `android_release_bundle.yml`)

- Explicit minimal `permissions`.
- Flutter pinned to 3.47.3.
- Every action pinned to a full commit SHA with the version in a comment.
- `flutter_ci.yml` runs on pull requests to `main` and on pushes to `main` and `claude/**`, uploads the resolved `pubspec.lock` as the artifact `pubspec-lock`, uses `--enforce-lockfile` once the file is committed, and accepts both `00NN_` and 14-digit timestamp migration prefixes.
- `pages.yml` deploys only after the website checks pass and no longer cancels a deployment in progress.

`isolated_e2e.yml` was outside this part of the work and still uses unpinned actions and a moving Flutter `stable`.

**Android** (`app/android`)

- `allowBackup="false"`, `fullBackupContent="false"` and `dataExtractionRules` that exclude everything from cloud backup and device transfer.
- The `http` scheme was removed from the App Link intent filter; the custom scheme stays.
- `isMinifyEnabled` and `isShrinkResources` are explicit for release, with a minimal `proguard-rules.pro`. The hard failure on missing signing configuration is unchanged.
- `app_android.iml` removed; `*.iml` ignored.
- Not done: `distributionSha256Sum` in the Gradle wrapper. The checksum could not be verified from this environment, and an unverified checksum is worse than none.

**Dependencies** (`app/pubspec.yaml`): `google_sign_in` removed (never imported; sign-in goes through Supabase OAuth). SDK constraint raised to Dart `>=3.9.0` with Flutter `>=3.35.0`.

**Ignore rules**: build outputs (`*.aab`, `*.apk`), credentials (`google-services.json`, service-account JSON, `*.p12`, `*.pem`, keystores anywhere) and local test output.

**Website** (`site/`)

- The privacy policy now covers staff email/password accounts, in-app notifications, warehouse and inspection records, where data is hosted, retention, user rights, and the deletion process step by step.
- One address per purpose on every page: `privacy@ruhamaa.com` for privacy and deletion, `support@ruhamaa.com` for support.
- The deletion page describes the in-app path, status tracking, what is removed and what stays anonymised, and the 30-day target. Its email link has an Arabic subject.
- The login-callback page explains returning to the app. It keeps `noindex`; the `Disallow` line was removed from `robots.txt`.
- English blocks carry `lang="en"`. "Last updated" is 11 October 2026.
- `tests/site/check_static.py` now also asserts the strict CSP, no inline script/style/event handlers, `rel="noopener"` on external links, and that every sitemap URL maps to a file.

**Tools**: `tools/branding/apply_identity.py --check` reports what it would change and exits non-zero, without writing. CI runs it.

**Documents**: `README.md`, `EXECUTION_PLAN.md`, `IMPLEMENTATION_STATUS.md`, `state-machines.md`, `ANDROID_RELEASE.md`, `GOOGLE_PLAY_RELEASE.md` and `PLAY_DATA_SAFETY.md` were corrected in place. `NAMING.md` is new. `RUHAMA_TIME_AND_SKILLS.md` was renamed to `TIME_AND_SKILLS.md`.

## 3. Manual steps for the owner

In this order. Each is done in a console; none can be done from the repository.

### 3.1 GitHub

1. **Create the `release` environment** (Settings → Environments): required reviewers (at least one person other than the usual release starter), *Prevent self-review* on, deployment limited to the branch `main` and the tag pattern `v*`, administrator bypass off.
2. **Move the four signing secrets into that environment** (`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`) and delete any repository-level copies.
3. **Set the three variables** (Settings → Secrets and variables → Actions → Variables): `SUPABASE_URL`, `SUPABASE_ANON_KEY` (the public anon/publishable key), `AUTH_REDIRECT_URL` (`com.ruhamaa.app://login-callback` for now).
4. **Protect `main`**: pull request required, required status checks (Flutter CI, Isolated E2E and Security, Website checks, Ataa identity checks), no force pushes. Without this the environment's branch rule protects nothing.
5. **Commit the lockfile**: download the `pubspec-lock` artifact from a green Flutter CI run and commit it as `app/pubspec.lock`.
6. **Verify the Pages custom domain** (account Settings → Pages → Verified domains, then the repository's Pages settings): `ruhamaa.com` verified with the TXT record and "Enforce HTTPS" on. An unverified custom domain can be claimed by another account if Pages is ever switched off.

Details: `docs/ANDROID_RELEASE.md` section 2, `docs/DNS_SETUP.md`.

### 3.2 Supabase

1. **Reconcile before applying anything.** Run `supabase migration list` against the production project and compare it with `supabase/migrations`. Production versions are timestamps that differ from the local `00NN_` prefixes, so resolve every difference (`supabase migration repair`) first. Do not run `supabase db push` on an unreconciled history; it would try to re-apply migrations that already ran.
2. **Apply the pending migrations to production**, after a backup and a staging rehearsal: `20260909235810_e2e_security_closure.sql` (recorded as not applied in the September handover), `20260915151416_ataa_display_identity.sql` if absent, and the migrations added by the October 2026 backend fixes. Deploy the Edge Functions from the same commit.
3. **Enable leaked-password protection** (Authentication → Sign In / Providers → Email → password security).
4. **Enable MFA** (Authentication → Multi-Factor) and require it for the administrator and supervisor accounts.
5. **Move the primary-admin identity out of public code.** The primary administrator's personal Gmail address is written in migrations `0020`, `0021` and `0026` and in `supabase/functions/admin-create-staff/index.ts`, in a public repository. That address is a phishing target and the single account that cannot be demoted. Do both:
   - rotate: make a dedicated project-owned Google account the primary admin and remove the flag from the personal one; turn on 2-step verification with a hardware key or passkey on the new account;
   - move: have the bootstrap read the address from private configuration (a database setting or Edge Function secret) in a new migration. Applied migrations cannot be edited, so the old address stays in history; that is why rotation comes first.
6. **Confirm the hosting region** of the project and state it in the privacy policy, which currently says the region is being confirmed.
7. Confirm the Auth redirect allow-list contains exactly the `AUTH_REDIRECT_URL` the release build uses.

### 3.3 Google Play and App Links

1. Build the first signed AAB with the workflow and upload it to Internal testing. Archive the symbols artifact privately.
2. Copy the **App signing certificate SHA-256** from Play Console (not the upload certificate).
3. **Publish the real `site/.well-known/assetlinks.json`** from `assetlinks.json.template` with that fingerprint, merge, and check `https://ruhamaa.com/.well-known/assetlinks.json` returns JSON.
4. Verify the App Link on a Play-installed build (`docs/GOOGLE_PLAY_RELEASE.md` section 7). Only then change `AUTH_REDIRECT_URL` to `https://ruhamaa.com/login-callback/`, add it to the Supabase allow-list, and build again.
5. Fill the Data Safety form from `docs/PLAY_DATA_SAFETY.md`: precise location is collected; deletion is reviewed, with anonymised records retained.

### 3.4 Mail and evidence

1. Confirm `privacy@ruhamaa.com` and `support@ruhamaa.com` receive mail. Deletion requests from people who cannot sign in arrive at the first one.
2. **Move `docs/handover-evidence/SECURITY_CLOSURE_2026-09-10.md` out of the public repository.** It is test evidence and was left untouched here, but it describes in detail the weaknesses the closure migration fixes, and the September handover recorded that migration as not yet applied to production. Keep it in private storage, and remove it from the public repository once it is archived.

- The Gradle wrapper checksum is not set.
- The deletion pages describe the reviewed process built in this pass; they are accurate only once the backend and app parts of the same pass are merged and deployed to production. Do not publish the site ahead of that.
